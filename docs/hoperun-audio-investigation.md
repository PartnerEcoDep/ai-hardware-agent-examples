## 2. 本次复测已确认的结论

1. **同一回答内取消重复预缓冲已经生效，但未解决完整故障。** 首次出现 `in_g711=240/pulled=0/queue=240` 是保留的首播等待；开始播放后的窗口出现 `960/960/0/writes=2`、`720/720/0/writes=2`，不足 1600 字节的小包已能继续进入设备。
2. **本次 Error -3 的直接原因仍为下行队列满。** 拒绝时 `incoming=240 queued=15872 capacity=16000`，剩余 128 字节不足容纳该包；随后 `reason=media_push type=0 bytes=240 push_rc=-1`。不是本次音频格式拒绝，也不是设备写失败对应的 -6。
3. 关联窗口 `window_ms=1320 in_g711=27600 pulled_g711=12752 queue=14848 device_pcm=3648 writes=27`。27600 字节相当于 3.45 秒的 8 kHz G711A 音频，说明存在集中交付；不能据单个窗口认定云端长期发送过快。拒绝记录和汇总属于不同线程/采样时刻，不能把队列快照当成同一瞬间。
4. `gap_max_ms=470 write_max_ms=100 output_wait_max_ms=0`；拒绝时 `last_loop_age_ms=370`。循环间隔包含最多 8 次阻塞写入，并非独立测得的“线程未获调度时长”。此前约 500–550 ms 的间隔也应按此解释。
5. 欠供窗口与集中交付同时存在；SDK 还出现发送队列满、停止超时。采集线程仍有持续读数，不能将 Listening 无识别直接归因于麦克风停采，也不能将 SDK 发送队列满与下行播放队列满混为一谈。
6. poll 请求 100 ms 而实际多为 200 ms 仍是确定的等待偏差，但与本次 Error -3 的因果关系未完成验证。

## 3. 原始示例与当前实现的具体差异

下表时长按 G711A 单声道 8000 字节/秒、PCM16 单声道 16000 字节/秒换算。原始代码个别注释中的“16 kHz”“DMA 水位”与实际路径不一致，应以配置及 BSP 实现为准。

| 项目 | 原始 GoldieOS 示例 | 当前 unified-app | 定位意义 |
|---|---|---|---|
| 播放/采集线程优先级 | 显式设置 21 / 22 | 不显式设置，BSP 默认为 10 / 10 | 改变与底层音频线程的调度顺序，优先单变量验证 |
| 音频线程栈 | 播放、采集均 8192 字节 | 均 8192 字节 | 不是当前已发现的栈大小缩减 |
| 下行格式与设备输出 | 默认 codec=0；G711A 解码后播放 8 kHz 单声道 PCM16 | codec=0；相同输出格式 | 不是简单的单双声道或采样率变更 |
| 解码位置 | SDK 音频回调先解码，再入队 PCM | 回调入队 G711A，播放线程解码 | 改变回调与播放线程的工作量分配；未证明导致卡顿 |
| 应用播放队列 | 16000 字节 PCM，约 1 秒 | 16000 字节 G711A，约 2 秒 | 当前实际容纳时长更长，不是队列缩小 |

| 每次设备写入上限 | 1024 字节 PCM | 512 字节 G711A 解码为 1024 字节 PCM | 当前调整版的单次写入大小已相同 |
| 设备补充目标 | `DMA_TARGET=6144` 字节 PCM | 4096 字节 PCM | 补充策略不同；6144 是目标，不是已证明可达的设备容量 |
| 补充批次与休眠 | 直到目标水位或应用队列空；根据水位 sleep 2/5/15 ms | 每轮最多 8 批、到目标即停、sleep 5 ms | 调度顺序无效后再分别验证，不与优先级同时更改 |
| 回答结束判定 | 应用队列空且设备剩余 <320 字节即停止 | 应用队列空且设备剩余为 0 才通知完成 | 主要影响尾部排空与界面状态，不足以解释回答中途满队列 |
| 下行队列满 | 拒绝整个当前 PCM 包、累计 `dropped_bytes`，继续会话 | 拒绝包、清理播放并报 Error -3 | 直接解释为何同类溢出在当前变成可见中断；不证明原版没有丢音 |
| 设备写失败 | 调用 `audio_write` 后不检查返回值 | 负返回报 -6 | 原版没有报错不等于没有设备异常 |
| 录音生命周期 | AUTO 会话开始创建/录音，结束停止并退出线程 | 应用初始化后持续采集，启停只控制上传 | 会话外资源占用、设备启动状态不同；会话中均持续采集 |
| 采集格式 | 640 字节 PCM16 双通道，左路麦克风、右路参考；转平面布局编码 | 相同帧大小，板级配置指定 mic=0、reference=1 | 帧布局一致；编码算法并非逐字节相同，见下文 |
| 会话 VAD | AUTO 显式 `convai_update` 设置 threshold=0.5、prefix=300 ms、silence=200 ms、允许自动回答和打断 | 不显式发送这组参数，使用 SDK/云端配置 | 与分句、打断、连续识别相关，必须单独核对有效参数 |
| TTS/启动参数 | 默认包含角色及指定音色，允许调用者提供启动配置 | `startup_json=NULL`，使用服务侧配置 | 未证明历史与当前使用相同音色/模型，不能排除包到达节奏差异 |
| SDK poll/TLS I/O 主路径 | 非阻塞 select + 固定休眠次数；非阻塞 TLS read/write | 同样的主路径，增加耗时日志 | poll 偏差不是此次架构整改新引入的算法，但可能受 SDK 交互方式影响 |
| TLS 校验/退出回收 | 未传 CA 时允许跳过校验；旧线程退出等待实现 | 保留证书校验、时间同步与退出回收修复 | 不是本轮机械回退范围，不能为对照关闭 TLS 校验 |
| 音频文件保存 | WS63 路径为空操作，实际文件写入仅 Windows | WS63 无音频文件写入 | 不能把原例的 WAV dump 调用认定为 WS63 文件系统阻塞 |

### 3.1 优先级差异的 BSP 证据

原始示例在调度锁内创建线程，然后分别调用 `goldie_thread_set_priority(..., 21)` 和 `(..., 22)`。当前 `ws_media_init` 直接创建线程，没有设置优先级。

本轮对最新 `out/goldieos.elf` 的相关符号重新反汇编，保存在本地 `build-hoperun-app/original-comparison-priority.txt`：

- `goldie_thread_create → osal_kthread_create → LOS_TaskCreate`，创建参数中的优先级为 10。
- `goldie_thread_set_priority → osal_kthread_set_priority → LOS_TaskPriSet`，数值直接传递，无反向映射。
- `audio_service_entry` 创建 `audio_task` 并设为 20；`audio_task` 创建处理音频的 `audio_thread` 并设为 20。
- `OsPriQueueEnqueue` 用 `0x80000000 >> priority` 标记就绪位；`OsGetTopTask` 用 `__clzsi2` 选择首个就绪队列。因此在当前 BSP 中，**数值越小，优先级越高**。

基于当前 BSP 的默认值，原始设置的顺序为“SDK 默认 10 → BSP 音频 20 → 应用播放 21 → 应用采集 22”；当前为“SDK 与应用播放/采集均 10 → BSP 音频 20”。SDK 本次诊断也记录 `thread=convai_io priority=BSP_default`。历史固件的实际线程设置是否成功仍需历史日志确认。

这足以确认调度关系变化，使原来优先运行底层音频的策略丢失；不等于已经证明驱动饥饿。应用线程也会阻塞/休眠，缺少运行时就绪队列或 CPU 追踪时，不能用优先级表直接推导停顿时长。原始 `convai_platform_ws63.c` 中“数值越大优先级越高”的注释与此 BSP 不符，不能作为调参依据。

### 3.3 编解码的实际对照

用现存 MinGW 编译原始 `convai_codec_g711a.c` 和当前 `ai_audio.c`，对两份真实函数执行穷举：

- 下行解码：256 个 G711A 码值全部得到相同 PCM，差异 0/256。下行解码公式变化不是本次候选原因。
- 上行编码：65536 个 PCM16 输入中有 61023 个编码结果不同；这只描述结果不同，不是“61023 个错误”。原编码的分段量化及负数处理与当前不同，不能宣称整个编解码链路逐字节等价。
- 两版上行都发送麦克风/参考的平面布局。编码差异可能影响上行波形、识别或参考信号，需要单独评估；不能用它直接解释已确认的下行队列满，也不应为了对齐原版而盲目恢复原编码器。

本地对照源码/可执行程序为 `build-hoperun-app/compare-original-codec.c/.exe`，不作为产品源码上库。该对照没有运行设备固件，也未覆盖实际 AEC、云端 VAD 或扬声器表现。

## 4. 当前判断与验证顺序

**确定的报错链路：** 下行数据集中入队 → 应用队列空间不足 → `push` 返回失败 → 当前云服务适配报 Error -3。仍需解释的是为何持续出现欠供、集中交付和积压，以及与上传队列告警的关系。没有证据表明“分层架构本身”必然导致卡顿，应验证迁移中具体的行为变化。

本轮原始代码证据将下一步顺序调整为以下单变量对照；此前“优先修 poll”的建议保留为历史分析，不再作为当前第一项：

1. **先只恢复应用音频线程优先级策略。** 在 GoldieOS WS63 媒体适配创建线程时显式设播放 21、采集 22，检查返回值；保留现有 SDK、首次预缓冲修复、容量、水位、批次、poll、TLS、日志及错误策略。限定 WS63，Windows 模拟器不直接套用 LiteOS 数值；不改其他平台。比较同板同网络的长回答、至少 5 轮连续对话、队列峰值、读写耗时、发送队列满及 Error -3。必要时回到 10/10 重复验证，避免偶然网络改善被误认作修复。
2. **再验证设备补充策略。** 优先确认实际设备软件环形缓冲容量和 `audio_write` 阻塞语义，再分别对照 4096/6144 目标水位、批次上限和休眠节奏。原版 6144 目标可能无法达到，不能直接认定增大目标就增加了硬件缓冲。
3. **隔离 SDK 与会话配置。** 优先取得原始流畅固件的版本/构建证据；需要对照时在原始示例中固定为当前 .835，与当前应用保持同 agent、有效会话参数及网络条件，再判断接入逻辑差异。SDK 切换、VAD 参数、音色分别进行，不同时改动。当前版本继续保留用户指定的 26.8.0 SDK。
4. **继续检查 SDK 收发等待。** 对 poll 使用单调时钟实际截止时间的修改单独验证；必要时测 TLS 已缓冲明文与 socket 就绪关系。固定休眠次数是原例共有问题，不能据此解释为架构迁移新引入的回归。
5. 若仍无法区分网络与设备链路，进行本地固定音频播放和受控速率/突发输入，验证 BSP 消费速率、欠供与溢出；随后才设计容量/背压或丢包策略。原例的“丢包继续”只改变故障表现，不能作为流畅性修复。

每轮保留独立固件哈希、日志、唯一改动及用户听感。判定改善应同时看内容完整性、长回答流畅度、连续识别和队列指标，不能只看 Error -3 消失。

## 7. 优先级对照实测：长停顿后自行恢复（2026-10-16）

用户反馈长回答仍严重卡顿，回答中途停在 Speaking，估计约半分钟后自行恢复。实际日志捕获到更长的媒体活动空窗。此次不应沿用上一版“满队列导致 Error -3”的解释：以下已完成长回答内未出现下行入队拒绝，最终收到 response.done。
