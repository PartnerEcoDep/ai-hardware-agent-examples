### 2.1 能力声明与匹配

能力分三个来源，分别版本化：

- 产品/设备：conversation.control、conversation.events、network.status、network.wifi_provisioning 等。
- 当前构建的测试接口：audio.digital_injection、audio.digital_capture、metrics.memory、metrics.audio_buffer 等。
- 测试台：fixture.acoustic_input、fixture.acoustic_output、fixture.power_control、fixture.reset、fixture.touch、fixture.screen_capture 等。

测试框架结合目标预期配置、设备握手声明和夹具声明决定能否执行。能力名称是协议契约，不允许适配器自行改变语义。每项能力可附版本、格式/容量约束和当前可用状态；“支持但暂不可用”与“不支持”分开。release 不因与 test 来自同一源码就声明测试能力。

| 情况 | 判定 |
|---|---|
| 产品不支持可选能力 | skip，附原因；必测项缺能力不能自动放行 |
| 宣称支持但行为不符合契约 | fail |
| 测试台、网络、云测试环境或夹具未就绪 | blocked/environment_error，不计通过 |
| 自动化尚未实现或证据不足 | not_covered，不能降级后仍算原测试通过 |

设备身份用握手和测试台绑定共同核对；COM 号仅是连接位置。无法区分多个同型设备时阻止自动部署，不猜测。身份生成方式待确认。

## 3. 统一会话契约

以下是外部规范模型，不要求直接替换现有内部枚举；适配必须真实映射，不能为了满足测试合成不存在的事件。

### 3.1 应用就绪状态

| 状态 | 含义 |
|---|---|
| initializing | 正在初始化 |
| not_ready | 初始化已完成，但 Start 前置条件不满足 |
| ready | 前置条件满足；是否能 Start 还需 session.state 为 idle |
| faulted | 存在阻止应用工作的故障 |

not_ready 附稳定原因：network_unavailable、time_not_ready、audio_unavailable 等。应用就绪与会话活动分开；网络变化时可同时出现 not_ready 和正在 stopping 的会话。

### 3.2 会话与音频状态

正常路径：idle → connecting → active → stopping → idle。连接失败或运行中断后也必须经过资源清理，最终回到 idle 并报告结束原因。

active 的活动提示为 listening、processing、speaking 或 unknown。无法从后端可靠判断的阶段报告 unknown，并提供可观测能力说明，不从任意日志猜测。

录音和播放分别报告 active/inactive/unknown；speaking 不代表录音停止，以支持全双工。资源故障由错误事件和会话结束原因表达，不把每种错误都增设为长期会话状态。

### 3.3 命令与完成条件

| 命令 | 前置条件 | 接受/完成语义 |
|---|---|---|
| conversation.start | 应用 ready 且会话 idle | 接受时分配 session_id；随后进入 connecting，成功到 active 或失败清理结束 |
| conversation.stop | 可以在 connecting、active、stopping、idle 调用 | active/connecting 时开始停止；stopping 时关联同一次停止；idle 时立即完成 |
| conversation.get | 协议可用 | 返回应用及会话快照、活动、音频状态、最近结束原因 |

约束：

1. Start 被接受不等于 Listening。用例必须等待明确事件或状态快照。
2. 已有会话时新的 Start 返回 invalid_state，不隐式重开；同一 request_id 重传按协议去重。
3. Stop 完成表示 SDK 会话及软件资源已清理，不再提交本会话音频，队列已终止；不保证硬件 DMA 尾音已消失。真实静音时延另测。
4. Stop 清理超时不能虚报 idle；报告失败及可观测状态，由恢复流程处理。具体清理预算待确定。
5. 对非当前 session_id 的定向 Stop 返回 session_mismatch，不误停新会话；无会话且指向最近已结束会话可返回已完成。清理用例可明确选择停止当前会话。
6. 断网导致结束后，网络恢复只恢复应用就绪，不自动创建新会话，维持当前产品策略。
7. 旧会话迟到事件不能修改新会话。session_id 与 boot_id 组合标识一次会话。
8. Start、Stop、UI 操作与 SDK 事件由现有应用 owner 串行处理；测试入口不跨线程直接改状态。
9. 暂停/恢复作为未来宿主扩展，本阶段不假定四目标已实现。

结束原因建议：user_stop、network_lost、connect_timeout、authentication_failed、audio_failed、internal_error。保留原始错误码及来源为诊断字段，公共用例不断言 -7 等厂商码。无法准确分类的错误归为明确的 unknown/internal 类别，不错误推断鉴权失败。

### 3.4 事件与顺序

首版建议提供 application.state_changed、conversation.state_changed、conversation.ended、operation.completed、operation.failed。响应接受异步命令后，应有带 request_id 的终结事件；Start 成功的 operation.completed 表示会话建立，conversation.ended 表示该会话后来结束，二者不能混淆。

Start 被 Stop 抢先取消时，Start 终结为 cancelled，Stop 按正常清理完成。每个已接受操作至多一个终结结果。具体 active 成功信号与 SDK 回调映射需在实现前核实。

## 4. 测试协议 v1 草案

### 4.1 传输与消息

语义采用版本化 JSON；三板优先串口，模拟器使用本地通道。串口有独立帧边界与日志隔离；波特率、长度字段/校验、最大帧长度、日志混传方式及本地 TCP/命名管道选择尚待确认，本文示例不是已可运行协议。

| 字段 | 适用消息 | 定义 |
|---|---|---|
| protocol_version | 全部 | 主/次版本，示例 1.0 |
| type | 全部 | request、response、event |
| request_id | 请求/响应，操作事件 | 当前控制连接中的唯一请求编号；重传保留 |
| boot_id | 设备响应/事件 | 每次启动变化，用于检测复位 |
| session_id | 会话消息 | 当前会话编号，非会话消息省略 |
| event_seq | 事件 | 同一 boot_id 中递增，发现事件缺口 |
| timestamp_ms | 设备响应/事件 | 设备单调时钟，不与主机时间直接相减 |
| method / event | 请求 / 事件 | 接口名 / 事件名 |
| status | 响应 | accepted、completed、rejected |
| payload | 按需 | 参数或结果 |
| error | 失败消息 | 稳定 code、可读说明和脱敏原始诊断 |

示例请求：

```json
{"protocol_version":"1.0","type":"request","request_id":"r-101","method":"conversation.start","payload":{}}
```

示例接受响应：

```json
{"protocol_version":"1.0","type":"response","request_id":"r-101","boot_id":"boot-42","session_id":"session-8","timestamp_ms":1200,"status":"accepted"}
```

示例建立完成事件：

```json
{"protocol_version":"1.0","type":"event","event":"operation.completed","request_id":"r-101","boot_id":"boot-42","session_id":"session-8","event_seq":12,"timestamp_ms":1850,"payload":{"method":"conversation.start","state":"active"}}
```

### 4.2 首版接口

| 接口 | 结果与限制 |
|---|---|
| device.describe | 协议版本、身份、固件/构建标识、构建配置、能力及约束 |
| device.get_status | 应用/会话/网络快照，快照对应 event_seq；快照一致性待实现保证 |
| events.subscribe | 选择事件类别；首版不承诺历史回放 |
| conversation.start / stop / get | 遵循上一节契约 |
| network.get_status | 连接状态、就绪原因；不返回密码或云凭据 |
| provisioning.enter / exit | 仅支持配网的目标；进入前停止会话，完成语义须区分请求接受与配网就绪 |
| metrics.describe / read | 可用指标、单位、范围、口径与采样值；不支持明确返回 unsupported |

数字音频、故障注入和逐项网络管理留作扩展。配网页 UI 测试必须实际操作页面，不能用协议直连成功替代页面验证。

### 4.3 可靠性、兼容与控制权

- 新控制连接先查询 describe/status；重连核对 boot_id。响应与事件均须可关联，不依赖到达顺序猜测。
- 声明有界去重窗口和容量。同一 request_id、相同参数返回原结果；参数不同返回 request_conflict。去重键需包含控制连接/客户端范围，防止不同客户端编号冲突。
- 超过去重窗口或重启后，不能盲目重传 Start；查询状态，再决定新操作。去重保留期、跨重连控制身份机制待确认。
- 超时分为应答超时、操作完成超时和用例预算；性能门限不等于等待超时。所有预算由配置给出，初始值需实测确认。
- 发现 event_seq 缺口时标记证据缺失，查询快照恢复当前状态；需要完整顺序证据的用例不能仅凭快照宣称通过。
- 协议主版本不兼容则拒绝控制；同主版本通过次版本和能力协商扩展，忽略可选未知字段。未知方法/非法参数有明确错误。
- 单设备一个测试控制者，测试台持有设备及夹具锁。控制连接断开后不改变正常产品策略；异常测试注入的撤销和租约超时恢复规则另行冻结。
- 明确队列和消息容量，指标采样不能阻塞音频或 owner 线程。事件溢出可观测，禁止无限缓冲。
- 测试控制仅在受控测试环境开放；release 不默认保留，权限及入口排除按构建方案处理。日志和报告必须脱敏。

建议稳定错误类别：unsupported、invalid_argument、invalid_state、not_ready、busy、session_mismatch、request_conflict、timeout、internal_error。环境错误由主控分类，不能将一切设备失败归为环境问题。

## 5. 指标与证据契约

| 指标 | 定义/待核实边界 |
|---|---|
| conversation.connect_duration_ms | 接受 Start 至确认会话建立，使用同一设备时钟 |
| conversation.stop_duration_ms | 接受 Stop 至软件清理完成，不是声学静音 |
| audio.playback_buffer_bytes | 指定软件播放队列的当前占用 |
| audio.playback_underruns | 有播放需求却无数据的事件数；起播预缓冲和正常结束不计，计数边界需核实 |
| memory.free_bytes | 必须附内存区域/堆范围；不能将 Windows 进程指标与 MCU 堆混用 |
| acoustic.response_duration_ms | 外部测量语音输入结束至设备可听输出开始；检测算法及阈值待确认 |

不支持返回 unsupported；暂无法采样返回 unavailable，均不伪造零。计数器标明按启动还是按会话累计。时间回绕处理与精度需声明。测试日志和指标的采样开销需要基线，关键性能在 release 复核。

每例保存目标身份、boot_id/session_id、协议/用例/语料版本、构建配置与产物哈希、源码版本/工作区状态、SDK、云配置追踪标识、测试台、事件、时间、结果及证据。数字注入、真实声学和模拟器结果独立分类。AI 内容采用版本化意图/语义标准，不固定匹配随机生成全文；识别成功需可观察证据，不能仅凭有声音推断。

### 6.1 test/release 覆盖

首版协议在 test 配置接入；构建区分尚未实现。release 是否保留受控查询另行决策，注入和内部干预默认排除。共同场景通过不同驱动执行：test 使用协议/数字音频，release 使用真实产品入口与外部证据。没有 release 夹具时注明未覆盖，不以 test 结果替代。

最终发布仍针对确切 release 镜像哈希验收。现阶段主机测试、既有人工验收和本计划的新自动化结果分别记录。

## 7. 待确认项与建议

## 8. 阶段 0 退出条件与后续顺序

阶段 0 设计评审完成须确认：四目标能力基线、会话状态与命令语义、首版协议范围、用例通过/失败/清理标准、待确认事项的责任人及冻结时点。Q01—Q06 应在对应接口编码前闭合；其余可随阶段完成，但未满足依赖的用例不能计入已覆盖或发布通过。

阶段 0 本身不要求已有协议实现或自动化通过。后续先做模拟器协议与用例，再利尔达串口，再实战派复用 ESP 实现，再润和后端；可以复用同一对话控制用例，不要求先完成无人值守烧写。首个实施验收点是 S00—S02、S05—S06 四目标通过，其他用例按能力与夹具逐步补齐。
