# AI 生态应用与硬件自动化测试架构设计

## src 产品源码与工程资料分离（2026-10-15）

当前产品源码位于 src/application、src/platforms、src/boards。application/core 管理状态与业务协调，services 提供能力，ui 展示状态；platforms 承接软件平台、入口、HAL 与构建适配；boards 负责具体板型。平台组件的 sdk 目录更名为 convai，内部函数名及 esp_sdk/ai_core/main 构建组件名保持兼容。

根 CMakeLists.txt 保留轻量分发，third_party、config、tests、tools、skills、docs 保留根位置。UNIFIED_APP_ROOT 指工程根，UNIFIED_SOURCE_ROOT 指 src；ESP 组件通过平台 cmake/paths.cmake 在组件依赖扫描与正常配置阶段获得相同路径。GoldieOS 独立入口也计算这两个根路径，不再依赖旧入口位置。

本轮保留功能实现、板型参数和产物名称；build-* 暂不收敛。src 只集中自研产品代码，第三方运行依赖归档放在 third_party；根 tools 保留架构检查和清单生成，不纳入一次性调试脚本。迁移旧 GoldieOS 入口的构建缓存时应重新配置；四目标编译通过不替代实机验收。


更新日期：2026-10-15。本文中的源码路径均相对于 unified-app 根目录；构建命令也在根目录运行。

本文整合整体架构、平台划分、跨硬件自动化测试和 test/release 构建方案。当前目录及实现边界是现状；后续章节中标为“建议”“规划”的接口、目录和构建配置尚未实现。2026-10-13 已实施当前平台目录与组件职责整改；测试协议、test/release 配置及未来平台仍为规划。

目标是统一 AI 能力和业务语义，支持不同系统及产品形态；新增具备既有能力的设备时，主要增加适配和配置，尽量不修改公共业务与测试用例。现阶段以利尔达、立创实战派、润和 WS63 和润和 Windows 模拟器四个目标验证设计。树莓派、Android、原生鸿蒙、iOS、原生 Windows 为规划范围，尚未确认对应 SDK、工具链或设备接入可用。

## 分层规则

- src/application/core 管理公共业务状态；不依赖芯片、板卡、RTOS、LVGL。
- src/application/services 提供可复用能力和协议；平台线程、设备 IO、网络栈和持久化由 platforms 承接。
- src/application/ui 负责页面呈现与用户命令，不负责云会话或硬件驱动。
- platforms 负责平台启动、依赖组装及平台接口；ESP-IDF 组件注册不代表源码是平台专用的。
- boards 负责引脚、外设初始化、显示传输及声道布局。src/boards/esp32/common/esp32s3 当前仅为两款 ESP 板共用。
- WS63 当前后端依赖 GoldieOS 服务 ABI。兼容该 ABI 的新 WS63 板主要新增 boards 实现；不同 OS/BSP 仍需 platforms 后端适配。

根 CMakeLists.txt 轻量分发目标，ESP 工程配置由 src/platforms/esp_idf/targets/esp32s3/project.cmake 设置 EXTRA_COMPONENT_DIRS 注册组件，媒体、网络、配置和 SDK 分别注册 esp_media、esp_network、esp_config、esp_sdk。GoldieOS common.cmake 组装 app、公共服务和板型，并调用六个组件的 component.cmake；运行环境差异在各组件的 ws63/windows 后端中选择。

## 第一批依赖优化（2026-10-14）

- ESP 的 esp_services 构建聚合已删除，media/network/config/sdk 分别拥有构建组件与公开 include；SDK 的内部 HAL 头仅在 SDK 模块使用。云配置通过 esp_device.h 获取设备 ID，不再引入 TLS、线程等内部类型。
- GoldieOS 的 ws_services.h 已拆成 media/network/config/ui 接口，各自放在组件 include；ws_app_events.h 仅声明应用拥有的事件投递入口。通过源码级 include 选项声明直接接口依赖，不向所有应用源码公开全部接口。固定运行包仍采用单目标构建，尚未实现全部第三方头文件的编译隔离。
- 板级契约按平台范围放置：src/boards/esp32/include/board.h 与 src/boards/ws63/include/ws_board.h；保留现有 esp32 板级目录名。WS63 接口不返回 AudioService、WLAN、WifiService 句柄。媒体与网络模块自行获取 GoldieOS 服务；runtime 等待基础驱动，boards 保留键盘、电源保持、显示与音频通道布局。头文件迁移不改变接口内容、功能或初始化顺序。
- ESP 专用显示句柄头位于 src/boards/esp32/common/esp32s3/include，由 ESP board 组件导出；板级契约分别位于 src/boards/esp32/include 和 src/boards/ws63/include，不设置跨平台公共板级头文件目录。
- 板级实现可以依赖其 BSP 的硬件驱动 API；板级公开契约不包含系统服务类型。当前 ESP 与 GoldieOS 的板级接口仍不同，本轮不强制统一音频驱动 ABI。
- 扩展优先考虑其他 WS63 伙伴和树莓派。兼容 GoldieOS ABI 的伙伴新增 boards 及 BSP 配置；不同 SDK 的 WS63 伙伴需要对应 platforms 后端。树莓派规划为 Linux 软件后端加板级外设配置，复用 C/C++ 公共业务，不复用 ESP/GoldieOS 句柄。暂不实施 iOS、Android、原生 Windows 或跨语言封装；现有 GoldieOS Windows 模拟器保留。
- 后续才统一应用流程、状态语义和测试协议；本轮不创建未来平台的空目录。

## 第二批：公共应用协调（2026-10-14）

新增 src/application/core/ai_controller.c，围绕已有 ai_app 状态机统一以下规则；两套平台仍分别提供线程和消息邮箱，不引入通用 OSAL。

| 公共协调职责 | 平台提供的适配 |
|---|---|
| 显式 Start/Stop、界面 Toggle、进入配网 | UI/按键转成 ai_command_t，回调转成 ai_message_t 入队 |
| 新会话先检查可信时间、重建云配置、再启动 | 时间状态查询、配置组装、媒体绑定及云启动/停止 |
| 配网前停止并失效旧会话 | 实际 SoftAP/接口切换；不支持配网的目标不提供回调 |
| 网络变化、连接超时、邮箱溢出处理 | 联网状态查询、单调时间、平台队列清空 |
| 网络提示每 500ms 检查、变化时刷新、统一校时提示 | 网络描述与 UI 文本提交 |

- 命令接口返回 0 表示已分发，不代表云端已连接；启动是否成功须查看状态或后续事件，未来协议不能把该返回值直接当作操作完成。
- 显式 Start 对活动会话无操作，不会像 Toggle 那样停止；重复 Stop 不重复调用云停止。原有界面按钮外观与交互不变，未增加串口协议。
- 云配置在启动初始化时尝试，失败记录后允许 Start 重试；ESP 不再永久缓存第一次配置失败。硬件/线程等致命初始化失败仍保留平台原有处理，不宣称已统一所有故障恢复。
- GoldieOS 配网命令不再通过独立 provision_pending 标志抢先执行，改为与事件进入同一 FIFO。邮箱溢出丢弃待处理消息并报告 -9，空闲时也可见；旧会话回调仍按 session 过滤。
- 保留原状态枚举显示语义：Ready 仍表示网络可用，未校时可见 Syncing time，尝试启动仍返回 -8。本轮没有实施阶段 0 的完整应用/会话/音频状态分离，也没有给 Ready 增加“全部资源均就绪”的含义。
- Windows 模拟器不提供配网回调，调用该命令返回不支持且不停止当前会话。未来 WS63 伙伴或 Linux/树莓派只需实现协调层所需回调与事件邮箱，不复制上述业务规则。
- 必要的 TLS 时间、NV、DHCP 网关和音频队列修复未改变；自动启动配网保留，断网恢复后仍由用户发起新会话。

## 第三批：公共网络契约（2026-10-15，已精简）

| 公共模块 | 已实现职责 | 平台仍负责 |
|---|---|---|
| src/application/services/network/ai_network_status | 网络状态、IP、热点名称和入口 URL 的值类型及统一提示格式 | 获取联网状态、同步、实际 AP/STA 切换、时间同步 |
| src/application/services/network/ai_wifi_store | 新增/更新、删除、设默认；最多 10 个网络；成功持久化后发布内存副本 | 存储加载、锁或单线程归属、介质读写、校验、代际及提交回读 |

网络状态查询现为各平台实现文件内的 static 函数；公开服务头只提供现有联网判断、网络描述和配网操作。公共状态结构用于内部格式化，不作为对外测试查询契约。未使用的 ai_wifi_store_clear 和 SsidManager::Clear 已移除；网页仍可逐个删除已保存网络。

网络状态不含密码。ESP 和 GoldieOS 的 description 包装调用公共格式化；Windows 模拟器保持原有 Windows network 文案和无配网行为。这是网络子系统快照，不是阶段 0 规划的应用/会话/音频一致性快照，也不能证明云端可达或 TLS 时间已就绪。ESP 查询由现有应用 owner 调用，不能将它直接当作任意线程可调用的测试协议接口。

保存规则：新网络放到首位，满 10 个时淘汰末位；更新已有网络密码不改变排序；设默认移动到首位。操作先修改临时副本，后端成功才更新当前内存。ESP 使用互斥锁，润和由网络线程独占。若介质提交成功而回读失败，接口仍报失败、内存保持旧值，但重启后可能读到新值；不能把失败等同于介质绝未变化。

ESP 的 wifi NVS 命名空间新增 profiles0/profiles1 两个带 CRC/代际的快照。仅在两个键都不存在时读取旧 ssid/password 系列键；首次成功修改后使用快照。旧键保留但不再同步，降级旧固件会看到旧网络记录；本轮不提供双向降级迁移。有效旧快照可以兜底损坏的新快照；两个快照都不可用时拒绝回退到陈旧 legacy 账号。启动加载失败时保存接口保持失败，需修复存储后重启；不会静默清空 NVS。ESP HTTP 任务栈增至 8 KB，为临时配置副本、回读副本和 NVS 调用保留空间，实板栈余量仍待验证。

润和仍使用原 NV 0x5100/0x5101 双快照和所有权检查，无需 SD 卡；本轮只接入公共列表操作，不更改其磁盘格式和启动恢复策略。两平台的加载失败策略尚未完全统一。快照是当前本地持久化格式，不是跨设备或串口线协议；未来 Linux 可采用文件/系统存储实现同一保存回调，不能直接假定 C 结构体跨 ABI 可移植。

按用户要求移除尚无调用方的累计音频统计、统计查询和队列统计字段；保留实际故障处理、连续失败计数、原有低频日志、播放缓冲与会话过滤。未来自动化测试需要指标时再定义采集入口和口径，不提前保留闲置接口。

扩展 WS63 伙伴时，兼容 GoldieOS ABI 的实现复用本次网络/媒体后端；不同 SDK 需要其实际平台后端。未来树莓派/Linux 复用公共列表操作和状态格式化，增加系统网络/存储/音频后端及必要的宿主文案，不将 Linux 差异放入 boards。本轮没有创建空平台目录，也没有实现串口控制、日志复用、设备发现或 test/release 配置。

必要修复继续保留：DHCP 网关、门户 DNS、TLS 时间、网络线程让出 CPU、可选音频输出配置、会话代际过滤、播放缓冲和 ESP I2S 写入时不持有队列锁。文件范围见 [第三批变更清单](changes-2026-10-15.md)。

## 后续整改：媒体契约归属（2026-10-15）

既有 ai_media_ops_t 与 ai_uplink_fn 从 src/application/services/cloud/include/ai_cloud.h 原样移入 src/application/services/media/include/ai_media.h。这是已被云服务、ESP 媒体和 GoldieOS 媒体实际使用的接口归位，不是新增抽象；类型名称、字段、回调、暂停返回值及上行停止屏障语义不变。

依赖方向为云服务引用媒体契约；两平台媒体头不再引用 ai_cloud.h。ESP 媒体因事件回调仍显式依赖 ai_app.h，但不依赖云生命周期或 SDK 头。ESP 构建中 ai_cloud 公开依赖 ai_media，esp_media 依赖 ai_core/ai_media；GoldieOS 仍沿用既有公共头目录，其运行包单目标构建边界未进一步改造。

check_architecture.py 增加媒体源码/头文件禁止直接引入 ai_cloud/convai 头的检查。主机云生命周期及云配置测试显式补充媒体头目录。没有改动 .c 业务实现、存储格式、网络流程或线程；不重新引入音频统计、公共邮箱、清空接口或单板 LVGL 配网。未来其他 WS63 或 Linux 后端实现既有媒体契约即可，不必通过云配置头获取媒体类型。

## 整体架构：统一契约，按需复用实现

| 层次 | 核心职责 | 复用与约束 |
|---|---|---|
| AI 会话与业务契约 | 命令、事件、状态、错误、取消及生命周期 | 各宿主遵循同一语义；允许不同语言封装 |
| 可移植业务与服务 | 对话状态机、云会话适配、音频处理、配网协议 | 优先复用现有 src/application/core 与 src/application/services，不依赖 UI 或具体硬件 |
| 系统能力适配 | 音频设备、网络、线程、同步、时钟、存储、SDK HAL | 按软件平台实现；音频处理算法与设备 IO 分离 |
| 应用宿主与交互 | 初始化、事件调度、前后台/暂停/退出、页面 | 固件、移动 App、桌面 App 可采用不同生命周期和 UI |
| 产品与硬件集成 | 外设、能力组合、默认参数、资源及构建选择 | 板级代码仅适用于确有硬件差异的目标 |
| 测试与可观测性 | 统一控制、状态订阅、指标与测试证据 | 复用真实业务入口，禁止另建测试专用对话流程 |

建议依赖方向：应用入口组装公共业务、服务、UI 和平台实现；UI 与测试入口提交相同业务命令，消费相同状态/事件；平台通过接口提供系统与设备能力。公共业务不能根据单板名称选择行为，应通过明确的能力和产品策略决定。

公共 UI 统一状态和交互语义，不要求移动端和桌面端使用 LVGL。Wi-Fi 配网与连接状态是独立能力；手机帮助外部设备配网，又不同于单板自身配网。配置接口可统一，但编译期配置、系统安全存储等实现不必相同。

优先定义三类契约：

1. 会话契约：启停、状态转换、异步事件、超时、错误类别、重复命令、会话结束和资源释放。
2. 系统能力契约：音频格式、设备读写、连接状态、配网、持久化、时间及能力缺失时的处理。
3. 宿主契约：初始化、运行、暂停、恢复、退出，以及音频被占用、权限变化和网络中断时的行为。

现有 ai_media_ops_t、状态机和事件机制是抽取契约的基础，不代表上述契约已经全部统一。SDK 平台可用性须单独验证，不能由架构支持推断。

## 平台、运行环境、板型和产品边界

| 维度 | 定义 | 归属示例 |
|---|---|---|
| 芯片/处理器架构 | 决定指令集、工具链、二进制 ABI | ESP32-S3、WS63、未来具体 ARM 构建目标 |
| 软件平台 | 应用访问系统能力所依赖的软件接口体系 | ESP-IDF、GoldieOS、Linux、Android、原生鸿蒙、iOS、Windows |
| 运行后端 | 同一平台接口在某种执行环境中的实现 | GoldieOS 的 WS63 实机后端与 Windows 模拟后端 |
| 应用宿主 | 应用依附的生命周期和执行方式 | 固件应用、Linux 进程、移动 App、桌面 App |
| 板型/设备配置 | 具体硬件连接、外设和设备布局 | lrd、szpi、hoperun、具体树莓派与外设组合 |
| 产品配置 | 功能组合、交互、资源与默认策略 | 无屏音箱、触屏助手、移动助手、桌面助手 |
| 构建目标 | 平台、后端、板型、宿主、工具链和依赖的组合 | 润和固件、润和模拟器、Android 应用 |

软件平台按适配接口划分，不要求必须是操作系统。运行后端仅在同一接口存在多个执行环境时拆分，不必为每个平台创建空后端目录。手机应用通常没有需要本项目维护的板级驱动。

| 目标 | 建议的平台归属 | 后端/宿主 | 板型或设备配置 |
|---|---|---|---|
| 利尔达 ESP32-S3 | ESP-IDF | 实机固件 | lrd，ESP32-S3 |
| 立创实战派 ESP32-S3 | ESP-IDF | 实机固件 | szpi，ESP32-S3 |
| 润和 WS63 | GoldieOS | WS63 实机固件 | hoperun |
| 润和 Windows 模拟器 | GoldieOS | Windows 模拟器进程 | 润和模拟设备配置 |
| 未来树莓派 | Linux | Linux 进程 | 具体型号及屏幕、音频等外设组合 |
| 未来 Android | Android | 原生应用宿主 | 通常无项目自有板级层 |
| 未来原生鸿蒙 | 原生鸿蒙 | 原生应用宿主 | 按产品设备能力配置 |
| 未来 iOS | iOS | 原生应用宿主 | 通常无项目自有板级层 |
| 未来原生 Windows | Windows | 原生桌面应用 | 系统音频、显示和输入设备配置 |

润和模拟器与原生 Windows 应用是不同目标：前者保留 GoldieOS 接口和润和应用体验，后者直接使用 Windows 宿主及平台能力。两者可共享业务，但不要求共享全部适配。

模拟器共用页面、业务和配置模型；独立提供虚拟显示、输入、网络、音频及设备身份。未来可分离 hoperun 实体配置与模拟设备配置，减少板级代码中的条件编译。

WS63 是芯片名称，不等于 GoldieOS 或润和。新 WS63 板采用兼容服务 ABI 时主要扩展 boards；若采用不同 OS/BSP，仍须实现相应平台后端。树莓派应作为 Linux 平台的具体设备组合，避免每增加一种 Linux 单板就复制一个平台。

### 平台层组织建议（待实施）

平台模块统一按 entry、media、network、config、ui、sdk 等职责理解。ESP-IDF 的组件注册机制与 WS63 的 CMake 组装机制可以不同；公共源码注册文件应与真正的平台实现分开。当前 GoldieOS 已按 components 划分功能模块，实机与模拟器差异放在对应组件后端中。运行时/线程接口按实际职责归属，避免新建含义不明确的公共杂项目录。

```text
src/application/core/、src/application/services/              # 公共业务和可移植服务
src/application/ui/                          # 当前共用 LVGL 与 web 页面
src/platforms/
  esp_idf/                   # app + 按职责组织的 components + 构建适配
  goldieos/                  # 已落地：components 按职责组织
    components/              # network/sdk/runtime 下选择 ws63/windows
    targets/                 # 两种构建入口
  linux/                     # 有实际目标时再创建
  ...                        # Android/原生鸿蒙/iOS/Windows 按接入需要增加
src/boards/                      # 需要硬件适配的目标使用
apps/                        # 未来原生应用的宿主与交互，按需建立
bindings/                    # 未来不同语言封装，按需建立
targets/                     # 产品及构建组合；初期也可由现有 CMake 承担
```

此树包含现有职责及未来扩展，实际目录以上文“当前目录”为准，不要求一次建立所有规划目录。contracts 若独立成目录，应承担接口与行为约定，避免只为了目录对称复制类型定义。

## Windows 主控的跨硬件自动化测试

### 核心目标和分层

同一用例描述行为，不判断 lrd/szpi/hoperun 等板名，也不包含端口、烧写命令或厂商错误码。新增具备既有能力的目标时，通常只新增目标配置、部署适配和必要的系统能力实现。

| 层次 | 职责 |
|---|---|
| 公共用例 | 场景、动作、断言和所需能力 |
| 场景/断言库 | 对话流程、音频判定、时延统计及资源趋势 |
| 统一设备接口 | 会话、网络、状态、指标与设备控制 |
| 目标适配器 | 构建产物选择、部署、启动、复位、故障恢复 |
| 通信适配器 | 串口、本地控制通道；协议语义不依赖传输方式 |
| 夹具适配器 | 声学播放/录音、触摸、摄像头、供电与复位 |
| 产品及测试台配置 | 门限、连接信息、设备身份、夹具绑定 |
| 报告与证据 | 结果、原因、事件、日志、录音、图像和产物标识 |

Windows 侧建议以 Python 实现主控。三款单板优先使用串口测试通道，以便被测 Wi-Fi 断开时仍能控制；模拟器使用本地控制通道。协议共用，通信方式分离。串口协议须有明确帧边界和日志隔离策略，不以任意文本日志匹配作为唯一判据。

### 设备协议与能力

握手返回协议版本、设备身份、固件版本、构建标识、test/release 配置和设备能力。每次命令带 request_id；会话事件带 session_id；启动实例或连接代号区分设备重启前后，事件序号用于发现丢失。规定应答、异步完成、超时、取消及重复请求语义，避免重试触发重复 Start。可变厂商错误保留为附加诊断，统一错误类别供用例断言。

首批接口范围：查询状态和身份、开始/停止对话、订阅事件、查询网络状态、进入/退出配网、按需采集资源指标。数字音频注入、内部异常注入为测试构建能力。测试入口调用真实应用命令并遵循现有线程归属，不直接修改状态机内部字段。

设备声明设备能力，测试台声明夹具能力；测试框架计算两者交集。无法提供的指标明确报告 unsupported，不能伪造零值。能力需版本和语义定义，连接后校验目标身份与预期配置，避免烧写或测试错误设备。

| 情况 | 结果规则 |
|---|---|
| 目标本来不支持该能力 | 可选用例跳过并记录原因；发布必测项不允许因此自动放行 |
| 声明支持但执行失败 | 测试失败 |
| 缺夹具、控制链路失败、云测试环境不可用 | 环境错误/阻塞，与产品失败分开；不能计为通过 |
| 尚未实现自动化 | 明确未覆盖，不自动降级成较弱的检查 |

示意用例（规划 API，尚不可执行）：

```python
@requires("conversation", "audio.acoustic_input", "audio.acoustic_output")
def test_basic_conversation(device, speech):
    device.wait_ready()
    device.conversation.start()
    device.wait_state("listening")
    speech.say("你好，请介绍一下自己")
    device.wait_event("response_started")
    speech.expect_output()
    device.conversation.stop()
    device.wait_state("ready")
```

真实声学和数字注入可共用场景步骤，但执行方式、判定证据和报告类别必须分开。固定语料应包含输入音频、格式、预期意图及版本。AI 内容判定与确定性状态检查分开；保存云端 Agent/配置版本或可追踪标识、SDK 版本、网络环境及重复次数，避免把回复文本随机变化当作固件错误。

### 四目标接入与覆盖范围

| 目标 | 控制方式（规划） | 部署方式 | 特有限制 |
|---|---|---|---|
| 利尔达 | 串口统一协议 | ESP 烧写适配 | 与实战派复用适配，Flash/配置不同 |
| 实战派 | 串口统一协议 | ESP 烧写适配 | 保留具体显示、触摸和声道配置 |
| 润和 | 串口统一协议 | 海思烧写及下载模式适配 | 无人值守复位尚需夹具/控制验证；可先人工辅助 |
| 润和模拟器 | 本地统一协议 | Windows 进程启动、退出和恢复 | 无 Wi-Fi 配网；性能不能替代 WS63 实机结果 |

| 测试类别 | 验证内容 | 必须记录的覆盖边界 |
|---|---|---|
| 主机测试 | 状态机、编解码、缓冲、协议 | 不覆盖实机驱动 |
| 软件集成 | 启动、会话、网络、异常恢复 | 控制成功不等于真实外设动作成功 |
| 数字音频 | 固定数据上行、下行、格式和音频处理 | 不证明麦克风或扬声器正常 |
| 声学闭环 | 外部播放语音，录制设备实际声音 | 固定摆位、音量、噪声条件；保存录音证据 |
| 显示/输入 | 画面及实际按键、触摸响应 | 软件命令测试不替代触摸硬件测试 |
| 配网 | 热点、DNS/HTTP、连接、保存/删除/默认网络 | 手机自动弹窗另需手机自动化或人工验收 |
| 性能稳定性 | 启停循环、长运行、资源、网络恢复 | 模拟器与实机分别统计 |
| 电气与功耗 | 上下电、复位、功耗和必要时序 | 需要外部仪器及明确采样条件 |

串口枚举不能仅依赖固定 COM 号；目标配置与握手身份共同确认设备，烧写后重新发现。每个设备/夹具须有独占租约或锁，防止并发测试互相干扰。每例定义前置条件、清理和失败恢复；超时有界。基础设施重试与产品失败重跑分别记录，保留首次失败，不用无限重试掩盖问题。

### 性能指标与报告

| 类别 | 建议指标及口径 |
|---|---|
| 会话 | 建连、云端首包、停止完成耗时；明确起止事件 |
| 音频 | 真实出声时延、缓冲占用、欠载/溢出、采集/播放错误 |
| 资源 | 堆可用量、峰值、栈余量、CPU；仅比较口径一致的指标 |
| 网络 | 连接耗时、断线、恢复结果 |
| 稳定性 | 重启、异常、连续运行时间、成功率及失败分布 |
| 外部测量 | 声学、画面、触摸和功耗；注明夹具、采样及校准条件 |

设备内耗时优先使用同一单调时钟；跨设备和 Windows 时间戳不得直接相减，需同步误差评估或由同一外部测量链路计时。云端首包与扬声器出声、业务停止与硬件静音分别定义。指标门限按产品配置和基线确定，不把 Windows 的进程内存与 MCU 的空闲堆直接比较。

报告至少包含用例/语料版本、源码版本及工作区状态、镜像哈希、SDK/工具链、目标身份、构建配置、能力、测试台、环境、步骤时间、结果分类、失败原因与证据位置。日志与录音按测试数据管理，凭据不进入报告；测试固件及含配置产物不作为普通源码提交。

建议目录（规划）：tests/host 保存主机测试，tests/automation 下按 cases、scenarios、contracts、adapters/targets、adapters/transports、adapters/fixtures、profiles、reporting 组织。设备端测试模块与 Windows 工具分开构建。

## test/release 构建与发布验收

两种配置共用同一源码、业务与平台实现，不维护独立分支或重复应用。四个目标各有 test/release 配置，初期可以按实施阶段逐步补齐，不意味着当前已存在八套构建产物。

| 配置 | 目的 | 能力与限制 |
|---|---|---|
| test | 集成、异常和内部性能分析 | 结构化控制、数字音频、故障注入、详细指标；显式启用 |
| release | 正式交付与发布候选验收 | 正常产品入口、必要诊断；禁止测试专用注入及内部干预入口 |

测试模块应由明确构建开关控制；测试固件自报 test 身份。release 不仅隐藏 UI，还须验证危险测试入口未被编译/注册。正式产品是否保留受控诊断协议是产品决策，不默认开放串口或网络控制接口。状态接口可在内部共用，外部暴露受构建和产品策略约束。

优化级别、业务参数、SDK、硬件配置尽量一致；记录差异和详细日志/采样引入的性能开销。测试构建的性能结果用于诊断，关键性能须在发布候选上复核。构建目录、缓存、生成配置和产物必须按目标与 test/release 隔离，避免继承测试宏；产物清单记录实际生效配置和哈希。

同一场景可在 test 下用协议控制和数字音频，在 release 下用真实 UI/按键、声学及图像夹具。具体步骤适配可以不同，不承诺所有测试逐行复用；真实证据缺失时不能将 test 结果替代 release 硬件验收。

发布流程：

1. 固定源码、依赖、工具链、产品配置与可追踪的云测试配置，构建 test。
2. 完成功能、异常恢复、内部资源与稳定性测试。
3. 从同一源码版本生成独立 release 发布候选并检查测试入口排除情况。
4. 对该确切镜像执行产品要求的真实硬件冒烟、关键性能及稳定性验收；未覆盖项显式阻断或由发布规则处理。
5. 直接交付已验收镜像，归档哈希、配置摘要、报告和证据；若重新构建或改变会影响运行的配置，重新确认对应验收。

## 分阶段实施计划与验收门槛

以下是顺序与交付条件，不是已完成事项，也不承诺在未准备夹具和云测试环境前实现无人值守。

| 阶段 | 实施内容 | 四目标范围与验收条件 |
|---|---|---|
| 0：冻结契约与基线 | 确认会话/系统/宿主契约、能力表、指标口径、协议、产品门限及测试清单 | 四目标建立当前版本和能力基线；区分支持、缺夹具、未实现；沿用既有人工验收作基线 |
| 1：平台职责整理 | 将 ESP UI 适配归位，平台按相同模块职责组织；区分 GoldieOS 共用代码和实机/Windows 后端；公共构建注册与实现分离 | 三固件及模拟器编译、现有 9 项测试通过；三板显示/配网/对话及模拟器 UI/对话人工回归；不同时改业务策略 |
| 2：测试接入与构建隔离 | test/release 开关及缓存隔离，设备协议、身份、事件、能力发现；Windows 主控与目标适配 | 先模拟器贯通协议，再利尔达，再实战派复用 ESP 实现，再润和；同一冒烟用例覆盖四目标，无板名分支；release 确认注入入口被排除 |
| 3：AI 与网络自动回归 | 数字音频、重复启停、迟到事件/中断、网络异常与恢复；语料、门限、报告及资源指标 | 四目标运行适用公共用例；三板执行配网测试，模拟器按能力排除；报告区分云环境错误和产品失败；失败可复现、证据完整 |
| 4：硬件闭环及性能 | 声学夹具、真实输入/显示验证、可控网络/供电、复位与下载模式控制、长运行 | 三板形成真实麦克风到扬声器证据；润和先解决可靠无人值守复位；模拟器单列结果；按产品门限统计，不互相替代 |
| 5：发布候选流水线 | test 全量与 release 关键验收、产物检查、哈希绑定和报告归档 | 三款 release 固件与模拟器 release EXE 使用确切产物验收并交付；不得只测 test；CI/定时运行在稳定夹具基础上接入 |
| 6：生态扩展 | 按业务优先级选择 Linux/树莓派或其他原生平台，验证 SDK，新增宿主/系统/语言适配 | 新目标复用既有语义和适用用例；能力相同的场景不改用例；只在新增能力时扩展契约并保留兼容性 |

阶段 2 的最小冒烟：查询身份与构建配置、等待 ready、Start、确认会话进入 listening、输入固定语音并观察响应、Stop、重复启停、超时后清理。没有输入与输出证据时，只能称为会话控制测试，不能称为完整对话或音频硬件测试。

开始实施前需要落实：测试语料和云测试配置、产品必测项与性能门限、串口和设备识别规则、复位/供电夹具方案、声学夹具及测试网络。可以先人工部署设备运行自动用例，报告注明“人工辅助”；无人值守是后续独立验收项。
